# Event-driven orchestration (`cloud_functions/`)

Moved from [CLAUDE.md](../../CLAUDE.md) on 2026-10-15 (verbatim) so the always-loaded file stays short. Keep this file current when the subsystem changes.

Fan-out pattern using two Cloud Run services that run one image (`cloud_functions/creative_fanout/Dockerfile`, built by the root `cloudbuild.yaml`; `FUNCTION_TARGET` picks the entry point and `FUNCTION_SIGNATURE_TYPE` its signature, default `cloudevent`; the root `cloudbuild.yaml` deploy step re-sets only the orchestrator's target, the worker's target/signature belong to its service; deployment/README.md §3). Since 2026-10-14 the orchestrator reaches the worker through a **Cloud Tasks** queue (`creative-worker-queue`: `--max-concurrent-dispatches=1`, 30-min dispatch deadline), the only worker transport: the Pub/Sub worker path (worker topic `creative-worker-queue-topic` + its Eventarc trigger, deleted 2026-10-15) was removed from the code on 2026-10-16 (`agent_worker_entrypoint`, `parse_worker_message`, `CRF_WORKER_TRANSPORT`, `CREATIVE_WORKER_TOPIC_NAME`; no Pub/Sub rollback, deployment/README.md §3 → No Pub/Sub rollback). The orchestrator's own trigger stays on Pub/Sub (the orchestrator trigger `creative-eventarc-trigger` keeps its dead-letter policy: 5 deliveries → `creative-crf-dead-letter`, pull sub `creative-crf-dead-letter-sub`, 7-day retention):
- **Modules:** `main.py` holds only the entry points (loaded by `functions-framework --source=main.py`): `crf_entrypoint` (`@functions_framework.cloud_event`) and `agent_worker_task` (`@functions_framework.http`); `messages.py` (trigger/worker message parsing incl. `parse_task_request`, `build_row_dict`), `orchestrator.py` (`dispatch`: check the Cloud Tasks settings → reap → select → mark QUEUED → create tasks), `worker.py` (`handle_worker_message` → `Outcome.ACK`/`RETRY`; `process_row`, `create_agent_run`, `build_campaign_state`), `status_store.py` (allow-listed SQL builders + `processed_status` statements, lock, reaper), `clients.py` (lazy BigQuery/Cloud Tasks singletons, per-invocation Agent Runtime client), `logs.py` (JSON log formatter), plus `completion.py`, `session.py`, `config.py`.
- **Orchestrator** (`crf_entrypoint`): Triggered by `CREATIVE_TOPIC_NAME` PubSub topic, queries BigQuery for unprocessed trends (oldest first, capped at `CRF_MAX_ROWS_PER_RUN`, default 3; a message's optional `max_rows` can only lower it), skips rows whose `trend_context` JSON has `"sensitive": true` (`COALESCE(JSON_VALUE(trend_context, '$.sensitive'), 'false') != 'true'`; plain `JSON_VALUE`, BigQuery rejects `SAFE.`), marks the selected rows QUEUED (by key, NULL/QUEUED rows only) **before** the first task, then dispatches one worker message per trend (`{bq_dataset, bq_table, row_data}`, `row_data` carrying the row key `uuid` + `target_trend`) as one Cloud Tasks HTTP task per row (`create_task` ≤ 30 s each; POST to `CRF_WORKER_URL` with an OIDC token of `CRF_TASKS_INVOKER_SA` (default the compute SA), audience = the URL; `dispatch_deadline` = `CRF_TASK_DISPATCH_DEADLINE_SECS` (default the worker timeout, clamped 15–1800); queue `CRF_TASKS_QUEUE` in `CRF_TASKS_LOCATION`; deterministic name `crf-<sha256(uuid, target_trend, processing_attempts or 0)[:32]>` (legacy rows: `entry_timestamp`), so `AlreadyExists` = already dispatched, never two tasks per attempt; any other error is counted and the row stays QUEUED); Cloud Tasks only: a missing or non-`https://` `CRF_WORKER_URL`, or no invoker SA, logs one ERROR per trigger and dispatches nothing, checked before any BigQuery work (rows keep their status; never a fallback). Shared by both: one lazy, lock-guarded BigQuery client + Cloud Tasks client per instance; BigQuery waits bounded by `CRF_BQ_QUERY_TIMEOUT_SECS` (60; `query_and_wait` + `job_timeout_ms`); JSON-line logs (`severity`/`message`); a malformed message (undecodable, missing fields, bad agent id/identifier) is logged as an error and ACKed, never NACKed into redelivery.
- **Worker** (`agent_worker_task`, HTTP, triggered by the Cloud Tasks queue; handler `worker.handle_worker_message`): the HTTP entry answers **200** for every recorded outcome (lost lock, PROCESSED, FAILED, re-queued) and for a body that can never run (malformed, not allow-listed, no engine), **500** for an error before the status write, which Cloud Tasks retries under the queue's own backoff (5 attempts, 60–600 s; never 503, which Cloud Tasks backs off harder and which may lower the whole queue's rate); it logs `X-CloudTasks-TaskName` / `X-CloudTasks-TaskRetryCount` as JSON fields (`cloud_tasks_task_name` / `cloud_tasks_retry_count`). Processes a single trend row by invoking Agent Engine — the engine is the worker's own `CREATIVE_AGENT_ENGINE_ID` env var (`config.CREATIVE_AGENT_ENGINE_ID`: the full `projects/<number>/locations/<GCP_REGION>/reasoningEngines/<id>` name or a bare id, normalised to the id; another project/region, a malformed value, or an unset `GOOGLE_CLOUD_PROJECT_NUMBER` (required on the worker: it builds the engine path from it; a full name's project part may be the number or the id) → `""` + one ERROR), never the message (trigger and worker messages carry no engine id since 2026-10-14; a legacy `agent_resource_id` is ignored with a WARNING when it differs); unset/invalid → each message is logged at ERROR and ACKed **before** the lock, so the row stays QUEUED; `deployment/engine_handoff.py apply --update-worker` sets it (`gcloud run services update creative-worker-crf --update-env-vars`, then `update-traffic --to-revisions <new>=100` because the service is traffic-pinned, verifying the new revision is Ready, carries the id and serves 100%; refused while a row is PROCESSING unless `--force`); it seeds the row's campaign fields plus `refresh_date` → `trend_detected_on` and `trend_context` → `trend_scout_context` as session state (`build_row_dict` / `build_campaign_state`; blank/NULL values skipped, and a table without `trend_context` still dispatches). A new `agentplatform.Client` per invocation, closed on its loop (each invocation is its own `asyncio.run`; a cached client's httpx transport stays bound to the first loop → `Event loop is closed`). **Completion check** (`completion.py` `RunMonitor`): a clean stream end is not success (spike 2026-10-13: a 499 failed `creative_pipeline` and the root ended the stream cleanly), so the row goes PROCESSED only when the session reaches `finalize_done`; the stream is bounded (`http_options.timeout` + a total timeout, `CRF_STREAM_TIMEOUT_SECS` 1500, clamped to the budget) and a timeout/cut is polled (`CRF_POLL_INTERVAL_SECS` 30) while events are still appended (a disconnected run continues server-side); an unfinished run gets ONE retry message on the same session (a copy of runserver's `AUTO_RETRY_MESSAGE`, drift-tested; the root re-calls `creative_pipeline`) **only on a positive end-of-invocation signal** (`invocation_ended`: the last content event is the root agent's (`CRF_ROOT_AGENT_NAME`, `root_agent`) final text, no function call since the last user message unanswered, stable across one poll; like runserver's `should_auto_continue`, duplicated), after a clean or an exception-ended stream alike — quiet time alone never retries (render/judge steps write no event for minutes); no signal + no new events for `CRF_IDLE_SECS` (600, ≥ 600) only gives up (`reason=stalled`); then FAILED unless finalized; the deadline is taken at **request start** in the entry point (`worker.run_deadline`: start + `CRF_WORKER_TIMEOUT_SECS` (1800) − `CRF_BUDGET_SAFETY_SECS` (150)) and passed down (`process_row(..., *, deadline)`); each session read is bounded by `min(CRF_SESSION_READ_TIMEOUT_SECS (60), remaining)`, the budget re-checked after it; the session delete after the check is best effort (`CRF_SESSION_DELETE_TIMEOUT_SECS` ≤ 30 s, logged, never raised, so it can't turn a finished run FAILED); config is one frozen `CrfConfig` (`config.load_config()`, clamped, read lazily through the `config.X` accessor; cross-checks: the safety margin ≥ read + delete + BigQuery timeouts, `REAP_STALE_PROCESSING_MINUTES` (default `ceil(worker timeout/60)+15`) ≥ the worker timeout, `CRF_MAX_ROWS_PER_RUN` ≥ 1, `CRF_WORKER_TIMEOUT_SECS` ≤ `CRF_TASK_DISPATCH_DEADLINE_SECS` (ERROR only: a shorter deadline frees the queue's one dispatch slot mid-run; the worker's `--timeout` must equal the deadline); an invalid combination logs an ERROR and falls back, never crash-loops); session user ids name the row (`<AGENT_WORKER_USER_ID>_<sha256(uuid, target_trend)[:12]>`, else `_<index>`); streamed events are logged compactly (`logs.pretty_print_event`: text ≤ 300 chars, never a whole event or `state_delta`, `event_author` / `event_kind` JSON keys); `AGENT_RUN_DURATION_SECS` carries `finalized` / `retried` / `reason`. Concurrency=1 (prevents duplicate processing), max-instances=1 (serializes runs under the project-wide pro/image quotas; with Cloud Tasks the queue's one in-flight dispatch keeps the instance from being asked twice, so no 429 bounces or mid-run redeliveries). Timeout=1800s.
- **Row state** (`status_store.py` `TRANSITIONS`, table in deployment/README.md §3 → Row states): rows are matched by trend_scout's MERGE key `(uuid, target_trend)` (`RowKey`; `entry_timestamp` only for ordering/logs, and the one-time match for a legacy message without the key, `reason=legacy_row_key`), and every UPDATE carries its from-state guard: mark QUEUED (NULL/QUEUED → QUEUED), lock (compare-and-set QUEUED with `processing_attempts` = n → PROCESSING, n + 1; returns the attempt, the **fencing token**), finish / requeue (PROCESSING at that attempt → PROCESSED / FAILED / QUEUED; 0 rows = `reason=lost_fence`, nothing changed), reap (stale PROCESSING → QUEUED, FAILED at `MAX_PROCESSING_ATTEMPTS`). A single-row statement matching > 1 row raises `AmbiguousRowKeyError`. The worker re-reads the locked row (`read_locked_row`, with the sensitive predicate as `crf_sensitive`) and builds the run from it, not the message (gone/sensitive → FAILED + ACK); a finished run's PROCESSED write is retried (up to 3 tries, each retry only while one more bounded BigQuery wait fits before the Cloud Run timeout) and never becomes FAILED (`reason=status_write_failed` leaves PROCESSING for the reaper); a transient error before a session exists (`SessionNotStarted` from `create_agent_run`: 429/5xx/timeout/connection on `runtimes.get` / `async_create_session`) re-queues the row (`reason=session_not_started`, `requeue` → FAILED at the attempt cap). Tests: `tests/test_crf_row_state.py` (fakes in `tests/crf_fakes.py`).
